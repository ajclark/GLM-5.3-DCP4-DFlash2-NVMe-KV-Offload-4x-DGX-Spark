• The human’s framing is right: repeated derivation is largely avoidable. But there are two different solutions: serialize immutable artifacts, or preserve the live executor.
  A weights-only daemon preserves less than you want; a warmed engine daemon, with a replaceable API container, preserves weights, graphs, kernel handles and NCCL
  connections.

  All allocation experiments below require a maintenance window; I ran none.

  ### A. Persistent tmpfs-backed parameters: plausible, performance unproven

  Shared physical DRAM does not guarantee identical GPU caching. NVIDIA documents registered-host memory as GPU-cached only with full system coherency; otherwise it is
  uncached. That is not sufficient evidence to promise cudaMalloc-equivalent performance on GB10. Memory-type distinctions
  (https://docs.nvidia.com/cuda/cuda-for-tegra-appnote/index.html#memory-management).

  MAP_SHARED plus registration can genuinely retain one physical weight copy. But only if initialization adopts those pages instead of allocating another 95 GB. A CPU tensor
  followed by .cuda() defeats this.

  PyTorch can wrap externally owned CUDA-addressable storage, with an appropriate lifetime/deleter. vLLM needs a custom initialization path: skip destructive repacking,
  reconstruct aliases/attributes, and account for memory outside its allocator. Today’s startup admission check (/home/napta2k/lmcache-mg/spark-src/vllm/v1/worker/
  utils.py:405) would reject the already-resident weights at utilization 0.91.

  Decisive experiment: sequential 256-MiB/1-GiB/4-GiB registered mappings versus cudaMalloc, measuring registration separately from page population, streaming bandwidth, an
  actual Marlin kernel, and graph replay after consumer restart. Approximately 23–25 million 4-KiB pages make extrapolating registration time unsafe; only a subsequently
  budgeted full-size test settles it. Check tmpfs capacity, memlock and cgroup limits. Hugetlbfs is a separate experiment, not an assumed cure.

  ### B. CUDA-IPC holder: plausible; preferable to A if supported

  Do not reject it merely because GB10 is integrated: NVIDIA’s Tegra guide says memory IPC became supported with CUDA 13 on newer open-driver platforms. GB10’s
  installed-driver support still needs a probe. IPC support update (https://docs.nvidia.com/cuda/cuda-for-tegra-appnote/index.html#cuda-features-not-supported-on-tegra).

  Decisive experiment: a 64-MiB cudaMalloc exporter and disposable consumer containers; repeatedly import, checksum, run Marlin/graph replay, and restart consumers while
  checking physical memory. Use explicit allocations, not arbitrary caching-allocator suballocations.

  The exporter must retain ownership. Daemon death is a fatal dependency failure requiring consumer restart/reload—not durable memory. IPC imports also require the custom
  adoption/accounting path above. If legacy IPC fails, separately probe CUDA VMM shareable allocations.

  ### C. Post-processed NVMe image: works architecturally; my first implementation choice

  Treat it as a versioned execution checkpoint, not a conventional state_dict: final tensor bytes, shapes/strides, aliases, scales, MLA plain attributes, and required non-
  tensor metadata. Key it by weights, fork/kernel build, quantization backend, architecture and parallel layout.

  Avoid “PWAL on empty weights”: postprocessing performs real transformations and parameter replacement. Separate metadata construction from transformation, then load final
  storage directly. The default loader (/home/napta2k/lmcache-mg/spark-src/vllm/model_executor/model_loader/base_loader.py:80) otherwise reruns postprocessing.

  Without GDS, O_DIRECT normally needs bounded registered host staging, then copying into device allocations; it cannot simply read into cudaMalloc memory. On UMA this adds
  traffic, not a second model-sized copy.

  Decisive experiment: round-trip one representative postprocessed MoE+MLA layer with aligned direct reads and bounded buffers; compare bytes and kernel outputs. Then
  maintenance-only full-rank loading measures whether 15–25 seconds is realistic. Ten seconds is the storage-only lower bound.

  Persist AOT/Inductor artifacts; the fork loads them before retracing (/home/napta2k/lmcache-mg/spark-src/vllm/compilation/decorators.py:565). Persist Triton binaries and,

  and unchanged manifests.

     remains alive—disabling it does not remove the live context. Clock controls (https://docs.nvidia.com/deploy/nvidia-smi/index.html)

     Change CPU governor to schedutil, preserving min/max: estimate 0–2 W. Heavy LPI-3 residency means cpuidle already does the important work; reported 2808 MHz does not
     mean every idle core runs continuously. Forcing 338 MHz mainly penalizes wakeup responsiveness. Leave idle states alone; unused LPI-2 is not inherently suspicious. Linux
     idle management (https://docs.kernel.org/admin-guide/pm/cpuidle.html)

     Software-rfkill Wi-Fi and Bluetooth: roughly 0–1 W combined; interface-down is not necessarily radio-off. Preserve previous block states.

     USB autosuspend: 0–1 W for idle peripherals, device-dependent. Use a tested device allowlist, excluding storage and recovery/input devices—not blanket powertop --auto-
     tune.

     These plus item 1 form warm idle: no NIC, PCIe, allocation, cache, or container changes.

  3. Cold idle: biggest plausible additional lever is ConnectX-7, not freeing RAM.

     attached and sibling functions active, achieves this. Qualify link-down/recovery with the human present; do not automate driver unload, PCIe removal, or forced D3.
     Release notes (https://docs.nvidia.com/dgx/dgx-spark/release-notes.html)

     Freeing 115 GB does not power off corresponding LPDDR capacity. Self-refresh is hardware/controller-managed; I know of no supported GB10 userspace control. Allocation
     occupancy is not memory activity. Cold restart also loses resident KV state.

  4. Human-present only: PHY speed, ASPM, aggressive device policies.

     Management 10G→1G might save 1–3 W locally, but renegotiating your only SSH link is a poor unattended trade.

     ASPM might save 0–3 W, but global policy touches management NIC, CX-7 and root NVMe. Leave default; avoid forced ASPM. NVMe already has APST: further tuning likely
     offers 0–1 W, with disproportionate timeout risk.

     Offlining 16 cores probably adds only 0–1 W over good idle residency, while complicating IRQ affinity and restoration. I would skip it. “Free RAM,” fixed minimum CPU
     frequency, and persistence-off with live clients are mostly placebo candidates here.

  5. s2idle + WoL: no unattended use.

     NVIDIA staff reported Spark WoL unsupported; advertised g does not prove platform wake support. That statement is older, so exact firmware testing matters. NVIDIA
     response (https://forums.developer.nvidia.com/t/cant-get-wake-on-lan-to-work/348168/4)

     Test only with someone able to physically recover one canary: stop the distributed stack, verify magic-packet delivery before suspend, check wake configuration, and arm
     an RTC alarm if supported—but do not treat it as guaranteed rescue. Test short and overnight intervals repeatedly.

     Assume RDMA/NCCL communicators require reconstruction; verify GPU health, Docker restart behavior and time synchronization. GPU suspend itself has a recent GB10 failure
     report. Report

     (https://forums.developer.nvidia.com/t/nvidia-suspend-service-fails-nv-set-system-power-state-warning-nv-c-4784-s2idle-suspend-does-not-complete-on-dgx-spark-gb10/380263
)

  6. Measure at the AC outlet before optimizing further.

     Cheapest useful instrument: a plug-in AC wattmeter; logging metering plugs are convenient, with switching schedules disabled. AC includes PSU losses. USB-C measurement
     requires genuine 48 V/5 A, 240 W EPR compatibility, not a generic 100 W meter. Electrical rating (https://docs.nvidia.com/dgx/dgx-spark/compliance.html)

     Compare repeated, thermally settled A/B windows. Log GPU power/clocks, per-CPU LPI residency deltas, wakeups and temperatures sparsely. None substitutes for wall watts.

  7. Make un-idle a verified transaction.

     Save an idempotent restoration journal outside containers; repeated entry must not overwrite the original baseline. Restore CPU online masks and every policy’s governor/
     min/max, persistence, and -lgc 2000,2000; confirm approximately 1995 MHz under work.

     Keep ingress closed until every check passes. Bounded retries only; failures must leave SSH intact and report the failed stage, never escalate automatically to NIC/GPU
     resets.

  ### The existing “pretend the cable was removed” commands

  For a human-present maintenance test, with the distributed serving stack stopped:

  # Power down CX7 with cables still physically connected
  sudo /opt/nvidia/dgx-spark-mlnx-hotplug/mtk-hotplug-handler.sh removal

  # Power it back up and rediscover its PCIe functions
  sudo /opt/nvidia/dgx-spark-mlnx-hotplug/mtk-hotplug-handler.sh plug-in

  This exact approach has a first-hand report of approximately 18 W savings with cables attached, followed by software restoration. Reported test
  (https://forums.developer.nvidia.com/t/disable-connectx-7-even-when-qsfp-is-connected-to-save-power/371302/5)

  The installed script explains why it works:

  - Lines 101–109: removes devices from CX7’s two PCIe domains, then writes 0 to debug_state.
  - Lines 116–129: writes 1, waits three seconds, then rescans both root ports.
  - Lines 20–46: requires /etc/nvidia/cx7-hotplug-enabled; otherwise it can exit successfully without performing the requested operation.

  Your enable file exists and hotplug is enabled. I also verified that domains 0000 and 0002 contain only their root bridges and the four CX7 functions. Your Realtek
  management NIC is in domain 0007, outside those targets.

  Do not just write 0 directly: the orderly device removal preceding hardware shutdown matters.

  ### Two things to fix before unattended use

  1. The shipped script is too optimistic about failures. Line 108 permits hardware shutdown if either domain removal succeeds—not necessarily both. remove() subsequently
     returns success regardless; plugin() also ignores rescan failures. Its presence test accepts any CX7 function, so a partial restoration can cause subsequent plug-in
     calls to skip recovery.

     I would harden this small userspace handler first: serialize manual/udev operations, require both domains fully detached before power-down, and verify all four functions
     after restoration. A custom kernel driver is not the first requirement.

  2. There is a relevant kernel-panic report involving mstflint_access. It can retain stale PCI-device pointers after hotplug removal; a later firmware query can trigger a
     use-after-free. Your node has this module loaded. The report concerns an earlier 6.17 kernel; I have not established whether your 1026 build fixes it. Resolve or isolate
     that module and its consumers before qualification—don’t run MST-based diagnostics casually after cycling CX7. Bug report
     (https://github.com/Mellanox/mstflint/issues/1786)

  ### What I would test

  One canary, physical recovery available: stop the cluster’s RDMA users, record wall watts, invoke removal, verify all four functions disappear and watts fall, then invoke
  restoration. Require four functions, both links at 200G, correct addresses/MTU, working RDMA and a distributed inference canary. Repeat before automation.

  This could recover approximately 72 W across four nodes, if your measured saving reproduces.

  The remaining architectural catch: this destroys existing NCCL/RDMA state. Preserving weights would require a separate vLLM suspend/resume mechanism that recreates
  communicators and affected CUDA graphs—not merely a NIC-driver change.
