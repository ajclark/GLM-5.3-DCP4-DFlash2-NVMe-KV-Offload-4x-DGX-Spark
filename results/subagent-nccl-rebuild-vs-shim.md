# Route B transport: patch NCCL and rebuild (option 2) vs. verbs interposer (option 3)

Subagent report, 2026-09-07. Read-only: `docs/JIT-PROXY.md`, `docs/CX7-POWER.md` §7, both prior
reviews, the fork at `~/lmcache-mg/spark-src/vllm`, and NCCL `v2.31.2-1` source (fetched from GitHub).
Nothing was run on the cluster.

## Verdicts

| option | verdict | one-line reason |
|---|---|---|
| 2, rebuild honestly | **feasible** | the IB backend's un-resettable state is four globals plus one cached count in NCCL core; ~150-250 lines in 3 files, and vLLM already has every primitive the worker path needs |
| 3, verbs interposer | **feasible-but-brittle, not recommended** | LD_PRELOAD cannot reach NCCL's verbs calls; the data path is inline through `context->ops`, so the shim must virtualize every verbs object and translate rkeys/QPNs in flight; the "wrap the IB net in a plugin" variant is option 2 with a different loader |

## Option 2: exactly what changes in NCCL 2.31.2

Facts that define the patch (all `src/transport/net_ib/` unless noted):

- `init.cc:25` `static int netRefCount`; `:281-284` `ncclIbFinalizeDevices()` is `netRefCount--; return`; `:287-289` `ncclIbInitDevices()` returns early on `if (netRefCount++)`; `:298` discovery only `if (ncclNIbDevs == -1)`; `:333` `wrap_ibv_open_device` once per device, stored at `:415` in `ncclIbDevs[n].context`; `:455-457` one detached `std::thread(ncclIbAsyncThreadMain, dev)` per port; `wrap_ibv_close_device` is called only on error paths (`:351`, `:463`).
- `common.cc:14-19` the globals: `ncclNIbDevs`, `ncclNMergedIbDevs`, `ncclIbDevs[]`, `ncclIbMergedDevs[]`, `ncclIbRelaxedOrderingEnabled`. `common.h:664-675` `fatalErrorCount` is only incremented; the only reset is `ncclIbStatsInit` at discovery (`init.cc:436`). `common.cc:33-39` turns a non-zero count into `ncclSystemError` on the next connect/accept, so after a cycle a *fresh* communicator fails loudly rather than hanging (useful for the gate experiment).
- Per-device state beyond contexts: PD cache `ibDev->pd/pdRefs` (`connect.cc:66-95`), MR cache `ncclIbDevs[d].mrCache` (`reg.cc:14-66`), GID snapshot (`init.cc:446`). Both caches are refcounted and drain to zero when the last send/recv comm closes (`connect.cc:1718-1790`), so a reset at refcount 0 can assert them empty rather than free them.
- The async thread already exits on its own after a device removal: `common.cc:170` and `:239` `break` when `ibv_get_async_event`/`ack` fail, which uverbs disassociation makes them do (after delivering `IBV_EVENT_DEVICE_FATAL`, `:177-181`). §7 reports "no NCCL log line at all" during the cycle; `common.cc:179` should have printed a WARN per port. The gate experiment must log whether the WARN appears and whether the `NCCL IbAsync` threads are gone (`/proc/<pid>/task/*/comm`).
- Core side, missed by both reviews: `src/plugin/net.cc:308-318` `ncclNetPluginFinalize` calls `finalize(ctx)` and decrements the plugin refcount but resets state (`netPhysDevs/netVirtDevs = NCCL_UNDEF_DEV_COUNT`, state `LoadReady`) **only for external plugins** via `ncclNetPluginUnload` (`:78-95`). The builtin IB plugin stays `Enabled` with `netVirtDevs` cached, and `src/graph/topo.cc:1759-1768` creates virtual NICs "only once per network": `if (nVirtualNics == NCCL_UNDEF_DEV_COUNT) ncclTopoMakeVNics(...)`. After an IB-backend reset that re-runs discovery (`ncclNMergedIbDevs` back to the two physical ports), the next communicator would skip vNIC creation and ask for the merged `f0+f1` device index 2, failing at `init.cc:575-578`. The reset therefore must also clear the core's cache.
- Net init is per communicator: `net.cc:165-215` calls `ncclNet->init(&comm->netContext, ...)` for every comm (`ncclIbInit`, `init.cc:527-537`) and `finalize` in `commFree` (`src/init.cc:405`, gated on `sharedResRefCount == 0`, i.e. per split family). The fork does not split: `VLLM_DISTRIBUTED_USE_SPLIT_GROUP` defaults to 0 (`envs.py:65`), `new_group` without `device_id` gives independent comms, so every comm destroy reaches `ncclIbFinalize`. Keep it that way.
- Port-recovery thread is refcounted and joined (`p2p_resiliency_recovery.cc:1470-1508`) and off by default (`NCCL_IB_RESILIENCY_PORT_RECOVERY=0`), so nothing to do there.

Patch (behind `NCCL_IB_RESET_ON_FINALIZE=1` so the stock behaviour stays default):

1. `init.cc`: in `ncclIbFinalizeDevices`, when `--netRefCount == 0`, call a new `ncclIbResetDevices()`: for each `d < ncclNIbDevs` assert `pdRefs == 0 && mrCache.population == 0`, stop and join the async thread, `wrap_ibv_close_device` once per distinct `context` (two ports of one HCA share one), `free(pciPath)`, zero the struct; then `ncclNIbDevs = ncclNMergedIbDevs = -1`, zero `ncclIbMergedDevs`. ~80 lines. The `std::once_flag onces[]` in `gdr.cc:73-77` cannot be reset; their cached answer (DMA-BUF support) does not change, harmless.
2. `common.cc` + `common.h`: make the async thread stoppable. Replace the blocking `ibv_get_async_event` loop with `poll()` on `context->async_fd` (exposed in `ibvcore.h:1027`) plus a per-device eventfd; keep the `std::thread` handle in `ncclIbDev` instead of detaching. ~60 lines.
3. `plugin/net.cc:308-318`: when an internal plugin's `ncclNetPluginRefCount` reaches 0 and the reset is enabled, set `netPhysDevs = netVirtDevs = NCCL_UNDEF_DEV_COUNT` and state `InitReady` so `ncclNetPluginInit` re-runs `devices()` (`:178-182`) and topo re-runs `ncclTopoMakeVNics`. ~8 lines.
4. Fatal counters and GIDs need no code: rediscovery re-runs `ncclIbStatsInit` and `ncclIbGidInfoQuery` (`init.cc:436, 446`), so a repacked GID index 3 is re-read.

Total 150-250 lines, matching Codex's spike estimate. Add one INFO line ("NET/IB : reset, closed N contexts") as the teardown acknowledgement token.

**Library instance and deployment.** vLLM's PyNccl loads NCCL with `ctypes.CDLL("libnccl.so.2")` by soname (`utils/nccl.py:17-34`, `pynccl_wrapper.py:330-337`); torch's `libtorch_cuda.so` has `libnccl.so.2` as `DT_NEEDED` in both pip cu13 wheels (`nvidia/nccl/lib/`) and NGC builds (`/usr/lib/aarch64-linux-gnu/`). The dynamic loader matches by soname, so both paths share one instance and one set of `ncclIbDevs`; the logs' single `NCCL version 2.31.2+cuda13.0` banner and `vLLM is using nccl==2.31.2` are consistent with that. Verify with `grep -c libnccl /proc/<worker>/maps` (must be one file). If torch turned out to link NCCL statically, torch's comms would live in an unpatchable copy and option 2 would require a torch rebuild or eliminating torch NCCL comms entirely; this is the first thing to check. Deploy by bind-mounting the patched `libnccl.so.2` over the image's path (the launcher already bind-mounts single files, `launch-glm53big-dcp.sh:166`); no `LD_PRELOAD`, no second copy. Build from `v2.31.2-1` with the GB10 gencode (`sm_121`) inside a CUDA 13 sbsa devel image; keep the version string so vLLM's checks pass.

## Option 2: vLLM side

Communicator inventory per worker, from the fork:

- `GroupCoordinator` (`parallel_state.py:351-470`) creates a torch NCCL `device_group` and a gloo `cpu_group` per group via `new_group`, a `CudaCommunicator` when `world_size > 1`, and an mq broadcaster over `cpu_group` (zmq/TCP for remote readers). `CudaCommunicator` (`cuda_communicator.py:73-80`) holds `PyNcclCommunicator`; custom allreduce is TP-only and disabled across nodes; symm-mem off.
- Groups with a real NCCL comm here: `_TP` (4 ranks, `:1766`), `_DCP` (2, `:1788`) and, missed by both reviews, `_EP` (4 ranks): `:1853` creates it whenever `model_config.is_moe`, EP enabled or not; `glm4_moe.py:132-134` caches its `device_group` (used only for `.size()`). `_PP/_PCP/_DP` are size 1, no device communicator. Torch NCCL comms exist lazily on any `device_group` used by `torch.distributed` (`broadcast`, `:722`; `send_tensor_dict`, `:844`) and possibly on the default PG, which was created with `backend="nccl"` (`:1606-1612`). The gate experiment must count `Init COMPLETE` lines per process rather than trust this list.
- No other RDMA users: the slab connector (`v1/kv_offload/tiering/`) has no distributed or verbs calls; the drafter (`dflash`, `draft_tensor_parallel_size=1`, `v1/spec_decode/dflash.py`) uses only `get_pp_group()` and the runner's groups, and its graphs are a `BreakableCUDAGraphWrapper` (`gpu_model_runner.py:5298`).

Order (all four ranks in lockstep; the gloo `cpu_group`s and the TCP store stay up; never call `destroy_model_parallel`/`destroy_distributed_environment`, `:2008-2054`, which also drop gloo and the default PG):

1. `EngineCoreProc.pause_scheduler(mode="wait", clear_cache=False)` (`core.py:1663-1704`; the in-proc variant rejects `wait`, `:740`) and wait for `_pause_complete`; `sleep(level=0)` is the same call (`:775-778`). Drain connector transfers.
2. Worker `suspend_network` via `collective_rpc` (`multiproc_executor.py:340-402`): the broadcast queue reaches headless nodes through `get_inner_dp_world_group().create_mq_broadcaster` (`:575`) over the LAN, workers dispatch by name in `worker_busy_loop` (`:969-994`), and `response_mqs` (`:376`) returns one result per rank, which is the four-rank acknowledgement the design asked for.
3. In the worker: `gc.unfreeze()` (the heap is frozen at `gpu_worker.py:788`), `torch.cuda.synchronize()`, `CUDAGraphWrapper.clear_all_graphs(); BreakableCUDAGraphWrapper.clear_all_graphs()` (`cuda_graph.py:170-175, 231`; the fork already uses this pair at `gpu_model_runner.py:6550-6551`), `gc.collect()`, synchronize again. This must precede any abort: `pynccl.py:148-153` documents that `ncclCommAbort` blocks until graphs that captured its ops are destroyed.
4. Destroy in order EP, DCP, TP: `g.device_communicator.destroy()` (fix `pynccl.py:154-160` to join the abort thread without the 5 s timeout), then `torch.distributed.destroy_process_group(g.device_group)` (a non-default PG, so gloo survives; torch's shutdown path is finalize+destroy, fine on a live idle device, verify in the image). Check the default PG for a lazily created NCCL comm and handle it the same way. Confirm zero `uverbs` fds in `/proc/self/fd` and the patched INFO line; return.
5. Proxy: `spark-idle.sh --down`. Later `--up`, then an in-container check of `/dev/infiniband` nodes and GID 3 value/type.
6. Worker `resume_network`: for each group, in construction order, `new_group(ranks, backend="nccl")` for every entry of `g.group_ranks` (`:436`; all ranks must call for all subgroups), then `g.device_communicator = CudaCommunicator(cpu_group, device, device_group, unique_name)`. Fresh ids are automatic: torch keys the store by group counter, PyNccl broadcasts its id over gloo (`pynccl.py:117-124`). Run a checked all-reduce per group. Re-capture with the elastic-EP pattern (`elastic_execute.py:498-515`): save and clear block tables, `unlock_workspace`, `model_runner.capture_model()` (drafter included, dispatcher keys still valid), restore, `lock_workspace`. Avoid the full `compile_or_warm_up_model` (`gpu_worker.py:640-800`): it re-runs autotune and `set_random_seed` (`:780`); if it is used, save and restore torch/CUDA/numpy RNG around it. `_release_cuda_graphs` from elastic EP (`:331-345`) is too heavy: it resets `torch.compiler`.
7. `resume_scheduler()`, then the proxy's real generation probe.

Effort: NCCL 150-250 lines plus a build/deploy day; vLLM 500-800 lines (worker methods 150-250, `parallel_state` rebuild helper 80-120, graph release/recapture 60-100, pynccl fix 20, EngineCore/executor/API 100-150, proxy hooks 50); tests on top. Two to three weeks for one person, gated by downtime windows. Wake estimate: 12 s adapter, ~1 s comm rebuild (`BOOT-TIME.md`: 0.4 s init), 14-20 s capture, probe; the 40-60 s target holds.

Risks: two NCCL instances (see above); cached handles in model code (`glm4_moe.py:132`, `openpangu.py:921` pattern) going stale, so audit `.device_group`/`.pynccl_comm` captures; `TORCH_NCCL_ASYNC_ERROR_HANDLING=1` and torch's heartbeat monitor killing a worker if a destroy stalls; RNG reset by warmup; `--device /dev/infiniband` (`launch-glm53big-dcp.sh:215`) creates static nodes, usable after the cycle only if uverbs minors are reused (expected, unverified; fallback is a `-v` bind mount plus a device-cgroup rule at the next relaunch); `NCCL_IB_GID_INDEX=3` pinned but re-read at rediscovery.

## Option 3: verbs interposer

- **LD_PRELOAD does not work.** `ibvsymbols.cc:79-94` dlopens `NCCL_IBVERBS_LIB`/`libibverbs.so[.1]` itself and resolves every verb with `dlvsym(handle, sym, "IBVERBS_1.1")`, which searches that object only. The supported hook is `NCCL_IBVERBS_LIB=<shim.so>` exporting versioned symbols (1.1, 1.8 `reg_mr_iova2`, 1.10 ECE, 1.12 dmabuf, 1.16 `query_port_speed`).
- **The data path bypasses the symbol table.** `ibvwrap.h:60-95` inlines `poll_cq`, `post_send`, `post_recv` through `qp->context->ops.*`; `ibvcore.h:1119-1131` inlines `ibv_query_port_ex` via `container_of` on the context. The shim must therefore hand NCCL its own `struct ibv_context` (`ibvcore.h:1023-1031`) with a shim `ops` table and facade `pd/cq/qp/mr` objects, keeping every field NCCL reads stable: `qp->qp_num` (`connect.cc:726, 1259`; `p2p.cc:621`), `mr->rkey/lkey` (`reg.cc:49`, `connect.cc:973, 1107, 1638, 1645`, `p2p.cc:551, 592`), `cq->handle/cqe`, `wc->qp_num/wr_id/imm_data/byte_len`, `event.element.*`. It must set `abi_compat != __VERBS_ABI_IS_EXTENDED` so the inline `query_port_ex` fails over to the intercepted `ibv_query_port` (`ibvwrap.cc:159-164`), and run with `NCCL_IB_DATA_DIRECT=0` because `init.cc:159-161, 378-381` pass contexts/PDs into `libmlx5` (`mlx5dvsymbols.cc:41-43`), which `container_of`s them into provider structs.
- **State to translate:** per fake object the real one re-created by device name (names are PCI-path stable), QP init/RTR/RTS attributes including `dest_qp_num`, `dgid`, `sgid_index`, `traffic_class` (`connect.cc:435-485`), ECE, MR `addr/len/access/iova` (RO path `reg.cc:41-46`), and a peer table old→new `(qpn, rkey)` exchanged after re-plug with the peer's shim (peer identified by the IPv4-mapped RoCEv2 dgid). Rewrite `wr.wr.rdma.rkey` on data writes (`p2p.cc:179`), CTS writes (`:400`), completion records (`:208`), speed updates (`:760`), flush reads (`:592`); rewrite `wc->qp_num` back. `remote_addr` is unchanged (same host VAs, GDR off).
- **What cannot be faked:** in-flight WQEs and their completions; the shim cannot see NCCL's request state, only its own posted-but-uncompleted count. With defaults it is zero at idle (recv WRs are posted per `irecv`, `p2p.cc:519`; pre-posting only with resiliency/OOO, `common.cc:90-104`), so quiescence must be guaranteed by the proxy, exactly as in option 2. PSNs start at 0 (`connect.cc:440, 502`) so continuity is moot. The old uverbs fd and UAR mappings are gone; NCCL never touches `cmd_fd`, but the async thread reads `async_fd` through `ibv_get_async_event`, which the shim must emulate and in which it must swallow `DEVICE_FATAL`, otherwise `common.cc:177-181` marks the device fatal and the thread exits for good.
- **Effort and fragility:** 2000-3500 lines of C, four to eight weeks, tied to the exact dlvsym'd symbol set (changes per NCCL release), NCCL's private `ibvcore.h` layout, and the protocol assumptions (pre-post off, resiliency off, GDR off, inline off, GIN/RMA off). Any NCCL or rdma-core update can break it silently.
- **Narrower variants.** Interposing at `ibvwrap` is patching NCCL, at which point the honest reset is simpler than handle virtualization. An external net plugin is a real option for *deployment*: NCCL dlcloses external plugins at refcount 0 and reloads them fresh (`net.cc:78-95, 314-317, 326-328`), which resets all static state and the core's vNIC cache for free; but 2.31.2 does not build `net_ib` standalone (`net_ib/CMakeLists.txt` only appends to `TRANSPORT_SOURCES`; no `ext-net/` at this tag), the code depends on NCCL internals, and the detached async threads still need the thread patch or dlclose crashes. So the plugin is option 2 with more build plumbing, not a cheaper option 3. The principled in-NCCL variant, extending `p2p_resiliency*.cc` (`ncclIbResiliencyReplaceQps`, `:68`) from port failure to device removal, is the largest of all.

## Recommended path and experiments

Option 2. Experiments, each in a downtime window, in the serving image with the launcher's exact flags and env:

- **E0, library layout** (no GPU needed): `ldd libtorch_cuda.so | grep nccl`, `/proc/self/maps` after importing torch and after `NCCLLibrary()`; find the `libnccl.so.2` path. Proves one instance and where to bind-mount.
- **E1, new-process all-reduce after a full cycle inside the container** (GLM's step): proves `/dev/infiniband` nodes, minors, GID 3 value/type, fresh uverbs.
- **E2, same-process gate, stock NCCL**: four persistent processes, gloo default PG over the LAN, `new_group("nccl")` for [0..3] and [0,1],[2,3], plus two `PyNcclCommunicator`s; all-reduce with checksums; capture and replay one CUDA graph containing a PyNccl all-reduce; destroy everything (join the abort threads); log `NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,NET` (context pointers at `init.cc:449`), uverbs fd count, `IbAsync` thread list; all ranks ack over gloo; cycle the adapter; log the `DEVICE_FATAL` WARN and thread exit; rebuild with fresh groups; all-reduce; capture again. Expected: loud failure at rebuild (`ncclSystemError` from `common.cc:33-39`, or `ibv_alloc_pd`/`create_cq` EIO). Proves the diagnosis and that stale contexts (still 2 open uverbs fds after destroy) are the only blocker.
- **E3, same with the patched library bind-mounted**: expected zero uverbs fds after destroy, the reset INFO line, and a passing rebuild. Proves the transport fix. Repeat 10 cycles for leaks (fds, threads, RSS).
- **E4, vLLM on a test lane**: `suspend_network`/`resume_network` over `collective_rpc` with the pause; measure wake; check retained-prefix hits and a generation.

## What the prior reviews got wrong or missed

- Codex ruled out "dynamic plugin reload"; NCCL 2.31.2 does unload and reload *external* net plugins cleanly (`net.cc:78-95, 326-328`). It is unattractive only because `net_ib` is not built standalone and the async threads must be joinable anyway.
- Neither review saw the core-side cache: `topo.cc:1759-1768` plus `net.cc:407` make vNICs once per process, so a backend-only reset would still fail on the merged `f0+f1` device.
- Neither review inventoried `_EP`: it exists for every MoE model (`parallel_state.py:1853`), so there are three PyNccl comms, and `glm4_moe.py:132` caches its torch group.
- GLM's "ncclCommAbort or the threads leak" describes the post-mortem state of §7. In the designed flow teardown happens on a live device before power-off, so graceful destroy is correct and abort is the fallback; the leak to prevent is the two detached `IbAsync` threads, which the patch joins.
- JIT-PROXY §5's "keep a persistent Gloo control world" already holds: every group's `cpu_group` is gloo and survives as long as nobody calls the generic destroy functions.
- §7's "no NCCL log line at all" contradicts `common.cc:179`; treat it as an open question for E2, not a fact.
