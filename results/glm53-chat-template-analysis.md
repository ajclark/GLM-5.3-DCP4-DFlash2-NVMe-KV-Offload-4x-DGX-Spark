## GLM-5.3 chat template (zai-org commit aca966e) vs. what we serve

**Provenance.** The HF template was byte-identical from the initial commit 7cda819 (2026-08-27) through 5bcee3f; only aca966e (2026-09-04 06:41 UTC, ZHANGYUXUAN-zR) touched it: *"chat template: early break in tool result reordering check — Following the optimization in this SGLang PR (sgl-project/sglang#36957), added four `break` statements so the loop stops early once it detects that the results can't be reordered."* No discussion thread on the repo mentions the template. Our `chat_template.jinja.bak-prethinking` is byte-identical to the pre-fix HF file (md5 e4c9e100…); our served `chat_template.jinja` (md5 cdfea119…, identical on spark-06c4/365c/ddbf/a218 and inside the running container at `/models/glm-5.3/chat_template.jinja`) is that file plus one local line.

**Exact diff, served → new HF (three things, nothing else):**

1. `visible_text` macro: `{%- else -%}{{- content }}` becomes `{%- elif content is not none -%}{{- content }}`. Previously a `null` content rendered the literal string `None` (I reproduced it: an assistant tool-call turn with `content: null` rendered `</think>None<tool_call>…`; a null tool result rendered `<tool_response>None</tool_response>`). Not mentioned in the commit message.
2. Four `{%- break -%}` lines inside the `ns_chk.can_sort` scan (the block that checks each tool result has a unique id matching a preceding tool call before reordering results into call order). Pure control flow; rendered output is unchanged.
3. Our local edit is absent. HF: `<|assistant|>{{- '<think>' -}}`. Ours: `<|assistant|>{%- if enable_thinking is defined and not enable_thinking -%}{{- '<think></think>' -}}{%- else -%}{{- '<think>' -}}{%- endif -%}`. HF's position is documented in the vLLM recipe: "Thinking is always on — the generation prompt opens a `<think>` block unconditionally."

**Unchanged in every version:** the prompt always opens `[gMASK]<sop><|system|>Reasoning Effort: Low|High|Max` (only `low`/`high` are honored, anything else → `Max`, per README: "accepts three levels: low, high, and max… defaults to max if not passed or set to any other value"); the `# Tools` system block with one JSON object per line inside `<tools>`; XML-style calls `<tool_call>name<arg_key>k</arg_key><arg_value>v</arg_value></tool_call>`; results as `<|observation|><tool_response>…</tool_response>` reordered to call order when ids allow; `clear_thinking` defaulting to `false`, so prior-turn thinking (from `reasoning_content`, or split out of a `</think>` in content) is re-rendered as `<think>…</think>` on every earlier assistant turn, and with `clear_thinking=true` only turns after the last user message keep it (README: "For chat scenarios, explicitly pass clear_thinking=true"). No special-token or literal-string changes; `<think>`, `<tool_call>`, `<arg_key>` etc. remain plain added tokens (ids 154841–154850), only `<|system|>/<|user|>/<|assistant|>/<|observation|>` are special.

**What it means for us**

(a) Parsers: `--reasoning-parser glm45 --tool-call-parser glm47` both resolve to `Glm47MoeParser` (`/home/napta2k/lmcache-mg/spark-src/vllm/parser/glm47_moe.py`), whose terminals are exactly `<think>`, `</think>`, `<tool_call>`, `<arg_key>`, `<arg_value>`; the new template emits the same strings, so parsing is unaffected. One trap: the parser reads `enable_thinking` from the *unfiltered* merged kwargs (`chat_completion/serving.py:259-266`), while the renderer drops kwargs the template does not declare (`renderers/hf.py:725`, `resolve_chat_template_kwargs`). With the HF template as-is, pi's thinking-off requests (`enable_thinking: false`, from `thinkingLevelMap.off: null` + `omitWhenOff`) would still open `<think>` in the prompt but put the parser in content mode — the model's thinking would stream as visible content ending in a stray `</think>`.

(b) Prefix cache / NVMe tier: I rendered all three templates locally over pi-style conversations (system + tools + assistant tool calls with `reasoning_content` + tool results + follow-up user). With thinking on, served and new are byte-identical for every case, including out-of-order results and `clear_thinking=true`. The only differences are (i) `null` content, which never reaches the template — vLLM normalizes `None` → `[]` → `""` (`chat_utils.py:1754`) and the server logged content format `'openai'` — and (ii) the generation prompt with `enable_thinking=false`, which is the last few tokens, so the prefix up to `<|assistant|>` still hits. Existing sessions and slab-tier entries stay valid either way. (Unrelated pre-existing caveat: changing pi's thinking level changes `Reasoning Effort: X` at token 3, which does invalidate the prefix.)

(c) DFlash: no token changes; the drafter sees identical prompt tokens. No effect.

(d) `reasoning_effort`: mapping unchanged. pi sends only `chat_template_kwargs` (the `chat-template` branch wins in `openai-completions.js`, so no top-level `reasoning_effort` is sent and vLLM's `enable_thinking` auto-injection at `protocol.py:490` never fires); request kwargs override the launcher's `--default-chat-template-kwargs '{"reasoning_effort":"high"}'`. pi's `minimal/low→low, medium/high→high, xhigh/max→max` remains correct.

Performance gain from the breaks is negligible for us: the quadratic scan is per contiguous tool-result block, and pi blocks are one to a few results; SGLang's numbers (0.16 s at 100 results, 10 s at 800 in one block) describe a single huge block, and their PR is a draft replacing the Jinja with Python, not something in our vLLM.
