**Original review**

Review complete; writing up findings now.

**Summary:** the plan's transport design is sound, but its two value-bearing claims, prepared runtime tensors and a 30 to 60 s switch, are not yet backed by a concrete contract in the vLLM 0.29 code it targets. The six findings below are ordered by how much they change the plan.

**1. The prepared-runtime restore contract already exists upstream and excludes the production quantization. Reuse it and say so.**
vLLM 0.29 has the exact mechanism step 4 asks for: `weights_already_processed()` at `upstream-vllm/vllm/model_executor/utils.py:20`, enforced by the guard at `upstream-vllm/vllm/model_executor/model_loader/utils.py:114`. The IPC cache loader shows the full restore recipe: meta-init the model, register exported params and buffers by name with an alias map, then run post-load processing in pre-processed mode, at `upstream-vllm/vllm/model_executor/model_loader/weight_cache/ipc_loader.py:185`. Only unquantized linear and embedding, block-wise FP8, KV-scale and unquantized MoE methods declare support. The recorded GLM launch uses CompressedTensors WNA16 with Marlin for both linear and MoE layers, whose post-load pass repacks and replaces parameters with new shapes, for example `upstream-vllm/vllm/model_executor/layers/fused_moe/oracle/int_wna16.py:661`. So the "explicit restore contract" is empty for the model this cluster serves and for every GPTQ, AWQ or Marlin model. The existing `sharded_state` loader is not an escape hatch: it copies kernel-format tensors into pre-processing parameter shapes and then the base loader runs post-load processing again, which is the double transform the plan forbids.
*Plan change:* define `ArtifactAdapter.restore()` as the ipc_loader recipe, make export use the daemon's `export_entries` semantics with `remove_duplicate=False` and aliases, and gate the prepared path on each quant method's `supports_pre_processed_weights`. Add "extend that flag to CompressedTensors WNA16 linear and Marlin MoE, verified against a disk-loaded baseline" as a named deliverable in order 4. Also carry non-tensor post-load state in the manifest, since KV-scale processing turns scale tensors into plain Python floats and the IPC path refuses non-FP8 quantized cache dtypes for that reason.

**2. The canonical path cannot be chunk-bounded, and its speed ceiling is far above the target. Split the transport into two explicit modes.**
Every native iterator yields whole tensors and every `weight_loader` consumes whole tensors in host memory, for example the transpose-and-narrow at `upstream-vllm/vllm/model_executor/layers/fused_moe/routed_experts.py:664`. The reader therefore has to assemble each logical tensor fully before yielding, so the real memory bound is "in-flight chunks plus assembled-but-unconsumed tensors," and the largest single tensor sets a floor the 512 MiB figure cannot override. Rank narrowing also still happens after the full tensor is read, so a canonical load reads the entire checkpoint per node, which the plan's own arithmetic puts at 81 to 101 s. The `DestinationWriter.submit(chunk)` contract only applies to the prepared path. One more caution: fastsafetensors and Run:ai "distributed" modes bind to the world group and redistribute tensors across ranks, at `upstream-vllm/vllm/model_executor/model_loader/weight_utils.py:1083`, which on this cluster means the single-channel NCCL ring, not local NVMe.
*Plan change:* name the two consumer modes. Mode A, canonical, wraps the whole-tensor generator behind `get_all_weights` so `DefaultModelLoader` semantics and `reload_weights` keep working, keeps the EP expert filter, and is documented as a correctness and fallback path with an 80 s class ceiling for GLM. Mode B, prepared, writes chunks straight into pre-allocated destinations and is the only mode the 20 to 25 s figure applies to. Require single-process, non-distributed library modes for either.

**3. Buffer ownership and deadlock rules need one concrete owner and a per-tensor admission rule.**
The plan says a buffer stays owned until the consumer's completion event fires, but on the canonical path the consumer is a native loader that copies on the current stream and returns without any event. The transport must record a CUDA event on the current stream after each yield returns and only free the buffer when that event completes, with no device-wide synchronize. The plan's `FREE→READING→READY→WRITING` states also admit a classic deadlock: the producer waits for a free slot while the consumer waits for the remaining chunks of a tensor whose size exceeds what is left in the budget.
*Plan change:* reserve a whole logical tensor's staging before issuing its first chunk read, and route tensors larger than the budget to the native low-memory path before the pipeline starts, never after partial reads. Add a host-memory line to the budget: the recorded load reported roughly 14 GiB of available host RAM at the start of weight loading, at `results/vllm029-upgrade/upgrade-029-r8/running-spark-06c4.local.log:2589`, so pinned staging competes with weights, KV and page cache on the shared 128 GB.

**4. All-rank activation of an unrelated model has no entry point in vLLM 0.29. Decide restart versus in-process before order 5.**
Workers load the model inside process construction, at `upstream-vllm/vllm/v1/executor/multiproc_executor.py:680`, before the cross-node message queues exist. The only in-process reload is `reload_weights` at `upstream-vllm/vllm/v1/worker/gpu_model_runner.py:5626`, which loads into the same module with the same shapes and layout. Config overrides are limited to `model_config` and `load_config`, and level-2 sleep snapshots every buffer to CPU and expects the same model back on wake. An unrelated-architecture B needs a new worker operation: tear down model, KV, graphs and connector, rebuild from a new config, re-run KV cache config, re-capture graphs, and reconfigure the scheduler and tokenizer. Rank readiness today is only "all RPC replies arrived," with no artifact-identity comparison.
*Plan change:* make the first milestone a restart-based switch that uses the loader plugin plus persisted caches, and state that in-process switching is order 6 or later. Specify the commit step concretely: each worker's load RPC returns artifact ID, compatibility key and generation, and the head refuses `initialize_from_config` on any mismatch. "Release partial allocations" is process exit in the restart design; in-process it needs the tagged memory pool the worker already uses for weights.

**5. The KV namespace identity breaks when weights come from a prepared artifact directory.**
The slab identity fingerprints the served model path by file name, size and mtime at `runtime/vllm029/overlay/vllm/v1/kv_offload/tiering/multinode.py:599`, and any identity change wipes the rank's slabs at `runtime/vllm029/overlay/vllm/v1/kv_offload/tiering/multinode.py:660`. Serving B from an artifact directory with no safetensors files yields a null or unrelated fingerprint, and A→B→A on one slab root wipes A's cache on each transition.
*Plan change:* compute one content identity at prepare time, hashing the original safetensors headers plus quant config and architecture the way `hash_checkpoint` does, store it in the manifest, and have the connector take it from the manifest when an artifact is active. Require one slab store per content identity and decide whether the 150 GB per-rank cap is per store or global, since two resident namespaces otherwise double the disk reservation.

**6. The 30 to 60 s objective needs a line-item budget, because the recorded log shows fixed costs the reader cannot touch.**
From the rank-zero log:

| Phase | Recorded | Removable by this plan |
| --- | --- | --- |
| Post-load Marlin repack, target | ~11 s | yes, by prepared runtime tensors |
| Draft model load, 4.58 GiB, replicated on every node | 10.4 s | yes, by putting the drafter in the same per-rank artifact |
| Gap before FlashInfer autotune starts, then two tune passes | ~35 s + ~6 s | mostly, if the cache survives container replacement |
| CUDA graph capture, target plus drafter | 5 s | no |
| Engine init total after model load | 58.8 s | partly |

The autotune cache is written under `/root/.cache/vllm` inside the container, which `runtime/vllm029/launch.sh` does not mount, while the Triton cache is mounted. Also the 35 s gap before the autotuner starts is unattributed in the log and should not be assumed to be tuning.
*Plan change:* replace the single objective with a budget: 21 to 26 s read, 5 s graphs, KV allocation and connector init bounded at 10 s, caches mounted so tuning is 0 s, and everything else must be pre-warmed. State plainly that a full container restart is outside 60 s until process startup and the 4-node NCCL handshake are accounted for. Mounting the autotune cache directory is a one-line launcher change worth doing now.

**Verdict.** Approve the transport and manifest design and the implementation order, with two conditions. First, rewrite step 4 around the upstream pre-processed-weights contract and name the quantization methods that must be extended, otherwise the prepared path serves no model this cluster runs. Second, split the 30 to 60 s claim into the itemized budget and commit to restart-based activation for the first milestone. Findings 2, 3 and 5 are specification gaps that will surface as bugs during order 2 through 4 and are cheap to fix in the document now.
