# Adaptive speculation for C1 coding and prose

Design, 2026-09-08; experimental phase completed 2026-09-09. See
[execution status](../results/adaptive-spec/STATUS.md) for completed work,
experiments, measurements, and unresolved promotion gates. Experimental policy defaults
to off; no policy has been promoted.

The objective is higher single-stream decode throughput and lower active
joules per emitted token while retaining the deployed GLM-5.3 target and
its verification rule. Ship two separately measured capabilities:
adaptive verification length first, then request-local copy proposals.

**1. Scope and operating assumptions**

Use the current TP4/DCP2, 180224-token window, DFlash2, compacted attention,
NVMe slab lane as the primary baseline. Keep clocks, quantization, prompt
templates, sampling parameters, context, and cache state matched across A/Bs.
The initial adaptive path applies to one active, pure-decode, greedy request.
Other requests use the existing full-seven-token proposal path. Concurrency,
mixed prefill/decode, structured output, cancellation, and preemption must
remain correct even when they cause eligibility to change mid-request.

Nonzero temperature and constrained sampling stay on the current path until
there is a separate sampling-correctness audit. Ordinary tool-call text is
part of the benchmark; grammar-constrained generation is initially excluded
from adaptation. Penalties and other logits processors need an explicit
eligibility audit before enabling adaptation for them.

This work reduces active inference work. It does not materially change the
cluster's idle hardware power. CX-7 cycling remains paused under the
September 8 incident decision.

**2. Separate the quantities the existing configuration conflates**

| Quantity | Meaning | Initial behavior |
|---|---|---|
| `draft_capacity` | Number of proposals generated by DFlash2 | Always 7; trained query block remains 8 |
| `verify_cap` | Number of those proposals selected for target verification | Initially fixed controls, then one of 1, 3, 5, 7 |
| `scheduled_verify_len` | Actual proposals scheduled after ordinary budget/stop constraints | At most `verify_cap`; authoritative for accounting |
| `proposal_source` | Tokens used for that verification | DFlash initially; whole copy proposal later |
| `accepted_prefix_len` | Leading proposed tokens accepted by the target | 0 through `scheduled_verify_len` |
| `emitted_tokens` | Tokens actually committed to the request | Includes replacement/bonus token, subject to termination |

Never implement this by reducing the launcher's `DFLASH_K` or mutating the
model's trained block size. Do not count a full DFlash block as seven
*verified* tokens when only a prefix was scheduled.

**3. Source inventory before implementation**

The deployed-source audit has now confirmed V2 `ModelRunner` and
`DFlash2Speculator`: the installed config forces V2 for this draft checkpoint.
Relevant source hashes match across all four ranks even though their image
digests differ. Exact graph/runner baselines and unmodified CPU-test kernel
fixtures are retained locally. The integration can leave `AsyncScheduler`
unchanged: trim its shared-placeholder list by assigning a slice before
scheduling, then let its original code replenish all seven future slots.
Existing scheduled-list lengths drive current-step rollback and accounting.

The following inventory describes the initial design audit; these ambiguities
are resolved by the running-source manifest in `results/adaptive-spec/inventory/`.

The checked-in overlay and locally available fork contain two runner
families. The legacy `gpu_model_runner.py` instantiates `DFlashProposer`;
the newer worker tree has `DFlash2Speculator` and `_selector_walk_kernel`.
The local DFlash2 speculator carries SM121-port changes. These source files
are evidence for the design, not proof of which classes the deployed image
actually executes. The launcher's image is the authority.

First implementation deliverable: a manifest of the image digest, effective
runner class, scheduler class, proposer/speculator class, sampler mode,
module paths and hashes, graph descriptors, and relevant effective config.
Inspect the image read-only and cross-check existing startup/trace records.
Snapshot the exact additional source files into `baseline/` before patching.
Do not replace this fork with upstream implementations as part of the work.

Observed integration points:

| Surface | Observation and required treatment |

**4. PR 1: measurement and a reproducible C1 workload**

Add a replay harness under `bench/` and a compact per-step telemetry record.
Keep `dcp_probe.py` as the deployment smoke test; its one prose and one code
prompt are too narrow to select this policy.

Use an initial screen of 12 prompts, then a locked evaluation set of at
least 30 prompts covering fresh functions, bug fixes, repository edits,
code continuation, tool-call text, explanatory prose, and creative prose.
Include short, roughly 32k, and roughly 100k contexts. Include thinking-off
and the actual coding-client thinking configuration without changing either
between variants. Separate development and evaluation prompts by task or
session, not random cycles from the same output. Synthetic copy-heavy and
no-copy cases supplement the real workload.

Per-step records should contain:

- Request ID, request incarnation, step ID, policy version, context length,
  eligibility, selected cap, actual scheduled length, proposal source, and
  feedback age.
- Accepted prefix length, actual emitted count, stop/length/grammar/budget
  censor flags, and whether the step was a full-length exploration probe.
- Cycle timing, actual and padded target token counts, graph descriptor,
  graph/eager mode, and draft query shape. Add detailed kernel timing only
  for designated profiling runs.
- Optional selected-score margin and entropy features from the DFlash2
  selector, if the active implementation exposes them cheaply.

Use existing completion feedback for scheduler-side counts. GPU-only
telemetry goes into bounded buffers with asynchronous draining; no new
`.item()`, device-wide synchronization, or per-token file writes in the hot
path. Audit dropped telemetry and measure instrumentation overhead.
Routine telemetry need not contain prompt text or candidate token IDs.

Record whole-cluster wall power over repeated, sufficiently long workload
windows, synchronized with request timestamps. Meter sampling is too slow
to attribute accurate energy to individual 100-150 ms cycles. Report total
active J/token, request energy including prefill, and idle watts separately.
Do not infer energy savings from a lower GPU utilization number.

Deliverables: harness, workload manifest, telemetry schema, baseline report,
acceptance histograms and instrumentation-overhead measurement. An initial
overhead budget is under 1% end-to-end; validate this with telemetry on/off.

**5. PR 2: fixed verification caps with an unchanged drafter**

Implement fixed caps before a learned or adaptive controller. Start with
caps 7 and 3, then add 1 and 5. They produce target query lengths 8, 4, 2,
and 6 respectively, while DFlash still generates its complete block.

The scheduler owns verification length. Store the decision in immutable
metadata for the step being scheduled, bound to request incarnation and
step ID. Apply it before budgeting tokens and allocating KV. Keep the
generation count passed to the drafter at 7 and its output buffers at a
seven-token stride. The runner copies only the scheduled prefix into the
target batch and uses the scheduled length everywhere in sampling and
rollback. Never mutate an already queued step when later feedback arrives.

Async placeholders must reserve the chosen next verification length, while
output placeholders and rejection correction refer to the length of the
step that actually ran. Use one authoritative decision on the scheduler
and the existing scheduler-output distribution to all TP/DCP ranks.
Rank-local confidence must not independently change tensor shapes or
collective counts. New requests or a mixed batch can switch future steps
back to 7; previously scheduled smaller steps must still complete correctly.

Keep conservative drafter lookahead allocation: it still needs all eight
query positions even when the target verifies fewer tokens. Tail proposals
and speculative draft-cache entries must not be treated as committed
context. The next draft consumes only valid target features and context
according to the existing rollback machinery.

Graph handling is a separate acceptance gate. Add only the required C1
graph shapes/descriptors, reusing a supported mixed-shape FULL graph path
where it is valid. A graph keyed as four target tokens must replay four
tokens of target GEMM/MoE work, with the fixed draft block correctly
represented whether captured inside or outside that replay. Inspect the
trace to prove this. Padding six tokens to eight, or masking four tokens
inside an eight-token target graph, may eliminate the expected benefit.
Cap extra graph memory at a proposed 512 MiB/rank and preserve measured
host-memory headroom and the daily context window; revise the shape set
if it does not fit. Do not trade memory safety for another policy choice.

Measure complete cycle latency by cap, including drafting, scheduling,
sampling, and graph dispatch. Use realistic routing traces: rejected target
rows still touch experts, so elapsed time is not determined by cap alone.
Eager execution is useful as a correctness control, not evidence that a
production graph variant is fast.

Include a separately labeled target-only reference if needed to assess
K=0. Do not claim a zero-proposal step skips drafter compute: maintaining
its state may still require work. Hot switching to a skipped-draft path
is deferred until draft-context catch-up is designed and measured.

**6. Offline decision gate**

For a fixed seven-token proposal, let A be its accepted-prefix length.
Ignoring end-of-request clipping, shortening that same proposal to k gives:

```
expected_emitted(k) = 1 + E[min(A, k)]
                   = 1 + sum(j=1..k, P(A >= j))
predicted_rate(k)   = expected_emitted(k) / measured_cycle_seconds(k)
```

Use this to screen candidates, not to claim end-to-end speedups. Different
block boundaries change subsequent draft inputs and trajectories; cap
timings and the final policy require live paired replays. A hindsight
choice using the eventual A is an oracle ceiling, not an implementable
policy. Exclude or explicitly model terminal and budget-clipped rows.

For illustration only: at a 144 ms full cycle with 2.7 emitted tokens,
baseline throughput is 18.75 tok/s. If a measured shorter cycle were 120 ms,
it must emit more than 2.25 tokens to improve throughput and more than
2.475 to improve it by 10%. Neither the 120 ms nor its acceptance is known
yet. Prose's low mean alone does not establish a win.

Proceed to adaptation only when the fixed-cap measurements and held-out
screen support a useful gain after overhead. If they do not, retain the
measurement result and evaluate the copy-proposal branch independently.

**7. PR 3: an async-friendly acceptance controller**

The first controller uses feedback already delivered to the scheduler from
completed steps. It deliberately tolerates the async pipeline's feedback
lag. It does not wait for confidence from the block currently being drafted.

The implemented version starts with eight completed full-seven-token
observations. Version 2 used an optimistic bound for unobserved acceptance
positions; its live development gains were only 3.5% for coding and 3.8% for
prose, below the prose gate. It spent too many cycles refreshing sparse tail
evidence. Version 3 instead uses a weak conditional acceptance prior from
separate fixed-seven calibration, with two observations' worth of weight.
The optimistic fallback remains when no valid prior is available. Held-out
prompts have not been used to fit this revision.
Maintain per-request, recency-weighted
prefix-survival estimates and a measured latency table by cap and context
bucket. Score available caps by expected emitted tokens / full cycle time.
Keep the current cap unless the estimated improvement exceeds a small
hysteresis margin (initially 3%); require adequate observations and revert
to the full-length prior when evidence is weak. These are development
defaults, to be calibrated before locking the evaluation policy.

Context tables may contain up to eight measured anchors. Interpolate cycle
costs and conditional priors between anchors, and clamp to the nearest
anchor within the declared operating range. Outside that range, use K=7.
An interpolated estimate does not establish a measured speedup at every
intermediate context. Snapshot and validate a request's table once, then do
only bounded arithmetic per scheduling step. The telemetry writer flushes
after activity and blocks indefinitely once idle, avoiding periodic idle
wakeups.

Handle censored observations with conditional acceptance risk sets: position
j contributes a trial only when it was verified and every earlier position
passed. Multiply the conditional rates to estimate prefix survival. Counting
tail failures after short rejections while omitting censored successful tails
would bias the controller toward short caps. A deterministic regression test
covers this selection effect. Schedule a full-length probe
every 16 eligible cycles,
to refresh the unseen tail and recover when prose turns into code. Include
the real cost of those probes in every result. Log the policy/action that
generated each observation; do not fit a tail model only on favorable
full-length cycles or pool conditional subgroups without checking bias.

Choose the fastest policy meeting the measured energy and latency gates.
Do not create a per-cycle energy estimator from a coarse wall meter. If
multiple policies have indistinguishable throughput, prefer the one with
lower measured active J/token.

Only after this version wins, evaluate whether current-block selector
features improve prediction enough to justify plumbing. Options are an
explicit measured host synchronization or a graph/runner design supporting
device-side choice with real smaller execution. Both require new timing
evidence. GPU masking inside the full target graph is not a shortcut.
Previous-block features can be piggybacked on ordinary completion feedback
without making the scheduler wait, and are a cheaper control.

**8. PR 4: copy proposals for coding, evaluated independently**

Begin with a request-local exact suffix match against prompt tokens and
already committed output. Use a small bounded lookup budget; prototype
with the existing n-gram implementation before adding a custom index.
Candidate match lengths 8, 16, and 32 are development choices. Measure
lookup cost at the full 180k window and warm all kernels before evaluation.
If the stock scan becomes expensive, use an incremental bounded index with
exact token comparison to reject hash collisions. No cross-request cache
is needed for the first version.

Keep DFlash running normally while testing retrieval, so its context stays
current and a fallback proposal is ready. Select either a whole retrieved
continuation or the whole DFlash proposal for the chosen verification cap;
do not splice a copied prefix onto a DFlash suffix conditioned on a
different predecessor. Require enough valid source tokens for that cap,
otherwise use DFlash. The target verifies the selected proposal as usual.

The lookup anchor must be the exact logical prefix at the next draft
position, including the latest committed replacement/bonus token. Async
CPU token history can lag or contain placeholders. Prefer the active
runner's GPU committed-token bookkeeping for the first integrated probe;
audit its rollback rules. A CPU/index implementation must validate its
request incarnation, prefix position and suffix against that GPU anchor,
falling back on any mismatch. All ranks must use identical source/IDs,
through deterministic committed history or the existing authoritative
proposal-distribution path. Avoid a new per-layer collective.

In shadow mode, compare retrieved tokens with the actual committed greedy
continuation at matching anchors. Full-seven baseline traces provide only
limited future-token coverage at a given anchor; request output can extend
that check, but cannot substitute for replaying retrieval's new boundaries.
Use observed copy acceptance and match features to calibrate the source
choice. Long matches are evidence, not a guarantee of the correct edit.
Do not label a retrieval match as accepted until the target validates it.

At first, retrieval changes the source within the already scheduled cap.
When late lookup results arrive, they must not resize that step. Longer
copy blocks beyond seven and skipping DFlash on copy hits are later
experiments, each with new graphs and explicit draft-context maintenance.
The first copy experiment claims only better acceptance, not saved draft
compute. Evaluate it with and without adaptive caps to separate the gains.

**9. Correctness and regression gates**

Add focused tests against the actual patched code, using this repo's
AST/Triton CPU harness where applicable:

- Exhaust every acceptance boundary for each cap, including zero accepted,
  all accepted, EOS, max_tokens, chunk/budget clipping, and bonus placement.
- Exercise cap transitions and lagged async outputs; assert consistent
  computed-token counts, output placeholders, fixed draft strides, token
  positions, rejection lengths, and request incarnation handling.
- Verify adaptive-off and fixed-seven use the baseline behavior. Test C1
  to C2 transitions, mixed prefill/decode, preemption/resume, cancellation,
  and unsupported-sampling fallback with earlier short steps in flight.
- Extend DCP causal-bound/slot tests to target lengths 2, 4, 6, and 8 at
  DCP1/2/4, with uneven shard boundaries and empty local candidate rows.
- Test censoring, probe updates, hysteresis, stale feedback and missing
  timing/config data. Weak or invalid policy state selects the baseline.
- For copying: overlapping matches, source-end limits, hash collisions,
  stale anchors, committed-only history, no-match fallback, and proposal
  switching with the DFlash cache still coherent.
- GPU integration: verify actual graph shapes on all ranks, no collective
  mismatch, no capture/JIT during steady decode, and stable memory.
- Slab integration: variable-cap generation, first-time store without an
  intervening warm request, eviction, engine restart and durable reload.
  The deployed `offload_prompt_only=True` intentionally excludes generated
  KV from disk. Preserve this policy: verify prompt-cache reload and correct
  continuation when previously generated tokens are supplied as input. A
  generated-KV disk-reload claim would require a separate configuration.

Use deterministic sampler/logit fixtures and committed-prefix differential
checks to establish algorithmic equivalence to greedy target decoding.
Count100 remains a byte-equality smoke test. Existing prose/code already
show shape-sensitive numerical drift, so end-to-end hashes alone neither
prove nor disprove correctness; investigate divergences at identical
prefixes and distinguish near-tie numeric differences from incorrect
tokens, positions, or cache contents. Run executable code checks and blind
prose comparisons in addition to invariants. Sampled decoding is a separate
future work item requiring RNG/distribution correctness, especially for
proposal-dependent stopping or mixed proposal distributions.

**10. Performance promotion and deployment**

Proposed promotion thresholds, fixed before the held-out run:

| Measure | Gate |
|---|---|
| Adaptive prose C1 | At least 8% paired central throughput improvement, with a 95% confidence interval above zero |
| Coding under adaptation | No more than 2% regression; gather enough repeats to resolve this margin |
| Copy branch | At least 8% on the predeclared edit/continuation subset, without more than 2% overall coding regression |
| Active wall J/token | No material regression; aim for at least 5% improvement on the benefiting workload |
| TTFT and p95 inter-emission gap | No more than 5% regression on matched cases; measure speculative bursts explicitly |
| C2/mixed/unsupported requests | Baseline policy and no material throughput regression |
| Memory and reliability | Daily context preserved, measured headroom retained, no hangs, stale KV, leaks, or new steady-state JIT |

Use balanced A/B order and at least three repetitions of the locked workload,
then increase repeats only when uncertainty prevents a decision. Bootstrap
paired differences by prompt/session, not individual cycles. Report prose,
fresh code, edits, and tool use separately; also report total emitted tokens
/ total decode time. Repeat power windows long enough for meter resolution
and thermal settling. Include lookup, telemetry, warmup, probe and feedback
costs; report cold and warm TTFT separately. Treat thresholds as project
decisions, not predictions of achievable gains.

Implemented configuration surface: `GLM_SPEC_POLICY=off|shadow|fixed|adaptive`,
`GLM_SPEC_VERIFY_CAP`, `GLM_SPEC_TRACE`, and `GLM_SPEC_COSTS`. Request-scoped
experimental controls permit paired comparisons within one boot. Cost tables
are scoped to the calibrated lane and context range; missing calibration
selects K=7. Copy proposals remain an offline opportunity screen.
Default is off. Add launcher preflight, exact overlay staging/checksums,
policy/config identification in results, and one-command restoration to
the current DCP2 lane. Use an isolated KV-tier namespace for experiments:
the existing overlay digest changes cache identity when code changes.
Do not weaken the slab identity gate to reuse production experiment data.

The implemented `bench/spec_experiment.py` preserves and restarts the exact
original containers, with isolated experiment caches, per-node pressure
watchdogs, and controller heartbeats. It avoids the generic rollout script's
NIC cycling, which remains paused after the September 8 incident. Use this
bounded experiment runner for testing;
run focused correctness checks before long performance jobs. First canary
is fixed-seven parity, then fixed-short verification, then adaptive, then
copy. Each capability can be retained or rejected separately.

1. Active-source manifest, replay harness, telemetry and baseline report.
2. Fixed-cap overlay with correct async accounting and real smaller graphs;
   measured cap/acceptance table and a go/no-go report.
3. Acceptance controller, focused tests, paired throughput/energy report.
4. Request-local copy proposal experiment and its independent report.
5. Documented rollout and a conservative default selected from the results.

3-5 for fixed caps and graph/async validation, and 2-3 for the controller
and evaluation. Copy integration is a separate roughly 3-5 days. Cluster
